近年、LLM が JSON などの構造化データを生成し、それを React や Vue のコンポーネントとして描画する「Generative UI」が注目されています。

ChatGPT にも GPT-6 と共にリッチなチャットレスポンスが実装され、皆さんも実際に目にすることが多くなったのではないでしょうか。

オープンなものとしては、[vercel-labs/json-render](https://json-render.dev/) や [OpenUI](https://www.openui.com/) などがあります。

Generative UI の基本的な仕組みは、端折って言ってしまえば、UI の構造をデータとして記述し、実行時にコンポーネントへ変換するものです。

この仕組みは、別に LLM と関係なく、何かに使えそうだな、と思いませんか。

特に、データの表示・編集・検索・操作が中心となる Web アプリでは、「画面構成を誰が決めるか」と「その画面をどう描画・操作するか」を分けるために使えそうです。

そこで、Nuxt 4、Nuxt UI 4、json-render を組み合わせて、Linear 風の Issue Tracker「Orbit」を GPT-6.1-Sol と [vercel-labs/fx](https://fx.sh) に作ってもらいました。

寝て起きたら出来上がっていたような PoC ですが、実際に動くものを見ていると、単なる JSON による UI 生成にとどまらない可能性を感じました。

リポジトリ > [halqme/json-render-nuxt](https://github.com/halqme/json-render-nuxt)

この記事では、なぜこの構成を試したのかを整理し、Orbit の仕組みと、使ってみて何が嬉しかったのかを紹介します。

## CSR・SSR とは別に決めたいこと

CSR では、ブラウザで UI を描画し、検索やフィルタリング、複数選択、楽観的更新などをクライアント側で処理できます。
静的なアセットを配信し、業務データの取得・更新は API へ任せる構成も取りやすいです。

ただ、一般的な CSR アプリでは、チケット一覧や操作メニュー、入力フォームなどの画面構成もクライアントのコードが決めます。
サーバーが権限や業務状態を管理していても、その情報を UI にどう反映するかはクライアントの実装で決まります。

SSR なら、サーバー側で初期表示の HTML を生成できます。
リクエスト時のデータやユーザーの状態を反映でき、JavaScript の実行完了を待たずにコンテンツを提示できる利点もあります。
一方、ブラウザ上でリッチな操作を続けるには、Hydration などを通じてクライアントの実装とつなぐ必要があります。

どちらを選んでも、画面構造と UI の実装が自動的に切り離されるわけではありません。
今回試したかったのは、クライアントの操作性を維持しながら、画面構成の決定をサーバーへ任せる設計です。

## 本当に欲しかった責務分離

チケット管理や業務管理のようなアプリケーションでは、次のような要件が同時に存在することがあります。

- 権限や業務状態に応じて、表示内容や提供する操作が変わる
- 複雑なデータモデルや業務ルールをサーバー側で管理する
- クライアントでは大量のデータをリアクティブに操作する
- 画面構造を変更しても、既存の UI コンポーネントや状態管理を再利用したい

このような場合、SSR と CSR のどちらを採用するかとは別に、設計上の選択肢がもう一つあります。
「どのような画面を構成するか」を決める責務と、「その画面をどう描画・操作するか」という責務を分離する、という選択肢です。

例えば、サーバー側では「この画面にはチケット一覧、ステータスフィルター、承認操作を配置する」と決定する。
一方、クライアント側では「チケット一覧を仮想スクロールで描画する」「フィルター操作をリアクティブに反映する」「承認ボタンの押下を Action へ接続する」といった処理を担う。

サーバーが画面構造を表すデータを返し、クライアントがそれを解釈して描画すればいいじゃん、というわけです。

これは **Server-Driven UI（SDUI）** と呼ばれるアプローチの一つです。

SDUI の採用事例としては、 Airbnb の Ghost Platform や Shopify の Remote UI などが存在しています。

しかし、それらの従来の主な導入動機は、複数プラットフォーム間での UI の統一、モバイルアプリのリリースサイクル、外部拡張の制御でした。

ここで冒頭の話に戻ります。

json-render は、LLM が UI を動的に生成するようになり、型付きの Catalog（利用できるコンポーネントの定義）、宣言的な Spec（画面構成を記述したデータ）、Renderer（Spec を描画する部分）の需要が高まったことを背景に作られたライブラリです。
これを使えば、クライアントのリッチな実装をそのまま活かしつつ、画面構造の決定だけをサーバーへ分離する構成を、単一の CSR アプリケーションでも取れるかもしれない、というわけです。

## json-render を使った Orbit の構成をさくっと紹介

> 寝ている間にできあがっていたアプリについて、エージェントへの聞き取りなどをもとにまとめた内容です。つまり又聞きです。

Orbit は、Nuxt 4 と Vue 3、Nuxt UI 4、json-render の Vue レンダラーで構築した Issue Tracker です。

My Issues、All Issues、Issue Detail、Projects という 4 つの主要画面を持ち、検索、フィルタリング、Issue の編集、コメント、新規作成などを操作できるみたいです。

Nuxt の SSR は無効化しており、ブラウザで UI を描画する CSR アプリケーションになっています。

例えば、Issue 一覧では、サーバーから受け取る UI Spec に「ステータス別にグループ化された IssueRow を繰り返し表示する」と記述されています。
ブラウザはその定義に従って、Issue のデータを一覧へ表示します。

IssueRow をクリックすると、Registry 側の描画処理がイベントを発火し、Spec で指定された Action が実行されます。
IssueRow コンポーネント自体は、どの画面に配置されているか、クリック後にどのような遷移を行うかを知る必要がありません。

この動作を支えるのが、次の 5 つの要素です。

- **UI Spec (server)**：画面構成を JSON で記述する。配置、繰り返し、表示条件、State への参照、イベントと Action の接続を定義し、API から配信する。
- **Catalog (client)**：利用可能なコンポーネントと、その Props、Events、Actions の契約を定義する。Orbit では 20 種類のコンポーネントと 7 種類の Action を定義している。
- **Registry (client)**：Catalog にあるコンポーネント名を、実際の Vue コンポーネントや描画処理へ対応付ける。Nuxt UI などの既存コンポーネントもここで利用できる。
- **Renderer (client)**：受け取った Spec を解釈し、Registry を使って Vue の UI として描画する。
- **State / Actions**：表示データ、検索条件、選択状態と、ユーザー操作に対応する処理を担当する。

サーバーが画面構成を配信し、クライアントがそれを描画する。
State と Actions が、そこへデータと操作を接続する構成です。

## 画面構造を独立した契約にする利点

じゃあ実際、この構成の何が嬉しいのでしょうか。

### 必要な部分だけを宣言的な UI にできる

json-render を使うからといって、アプリケーション全体を JSON で記述する必要はありません。

例えば、サイドバーのナビゲーションだけを json-render で構成し、メイン画面は通常の Vue コンポーネントとして実装することもできます。
あるいは、メイン画面の大部分を Vue で構築しながら、ユーザーの状態や権限によって構成が変わる詳細パネルや操作メニューだけを json-render に任せても構いません。

その際、json-render で描画する領域と通常の Vue コンポーネントは、同じ State や Action を共有することもできます。

画面の構成をサーバー側で決定したい部分だけを、ページより小さな UI 領域として切り出せるわけです。
既存の Vue コンポーネントや操作体験を維持したまま、部分的に導入できる点は魅力だと感じています。

### テストの対象を明確に分離できる

今回、特におもしろいと感じたのがテストとの相性です。

UI Spec がデータとして表現されているため、何を表示するかという定義自体を検証できます。

例えば、次のようにテスト対象を分けられます。

- UI Spec：利用可能なコンポーネント、Props、Binding、Action が正しく定義されているか
- Registry：各コンポーネントが正しく描画され、イベントを発火するか
- State / Actions：入力や操作によって、期待した状態変更が起きるか
- E2E：実際の画面で業務シナリオが成立するか

特に、画面構造そのものをテスト用の入力として差し替えられる点がおもしろいですね。
同じ Action を異なる画面構成から実行したり、表示要素を変更しても業務上の操作結果が変わらないことを確認したりできます。

もちろん、Spec の構造検証だけで画面の正しさが保証されるわけではないんですが、「何を表示するか」と「どう振る舞うか」を、異なる検証単位として扱いやすくなるのは嬉しいです。

### サーバーとクライアントの契約を明示できる

もう一つの利点は、サーバーとクライアントの間に、画面構造についての明確な契約を置ける点です。

一般的な CSR アプリでは、API から取得したデータや権限情報をどう組み合わせ、どの UI として表示するかはクライアントが決めることが多いです。

SDUI では、サーバーが業務状態とユーザーの権限に応じて、利用可能な操作を UI Spec へ反映できます。
例えば、承認権限のないユーザーに返す Spec には、承認ボタンやその Action への接続を含めない、といった構成にできます。

ただし、これは表示する UI を決める仕組みであって、操作の認可そのものではありません。
ボタンが表示されなくても API へ直接リクエストされる可能性はあるため、操作を許可するかどうかはサーバー側で検証する必要があります。
認可の判断は CSR でも実現できますが、SDUI では、その判断を反映した画面構成までサーバー側で決められるわけです。

## なぜ JSON なのか？

json を選んだ理由は OpenUI より json-render のほうが LLM が存在しないプロジェクトでも使いやすそうだったから、に過ぎません。

意味があるのは、画面構造を、次の性質を備えた中間表現として扱えることだと思います。

- **制約された表現力**：Catalog に存在するコンポーネントや Action だけを利用できる
- **構造化された表現**：解析、差分比較、変換、検証ができる
- **シリアライズ可能性**：実装コードから独立して保存・配信できる

Vue SFC も宣言的に UI を構築する仕組みですが、任意の JavaScript や composable、副作用を含められます。
リアクティブな UI を実装するには必要でも、既存のコンポーネントを配置してデータにつなぐだけなら、そこまでの表現力は必要ありません。

json-render では、Spec が使える表現を Catalog の範囲に制限します。
特殊な DataGrid や複雑なフォーム、独自のアニメーションは Vue で実装して Registry へ登録し、Spec では配置やデータとの接続を宣言する、という分担です。

Vue の実装能力を制限するのではなく、Vue で実装された機能を組み合わせるインターフェースだけを制限する。
そのため、画面構成を実装コードから独立して配信・検証できるのだと思います。

## 適しているアプリケーションと、そうでないもの

当然ながら、すべての Web アプリケーションに json-render が必要なわけではないです。

例えば LP やコンテンツ中心の Web サイトで、画面構成を別に配信する要件がなければ、SSG・SSR などで十分でしょう。
Inbox の項目を一覧表示して遷移するだけなら、データを受け取って Vue の `v-for` で表示する方が簡単です。

既存のローコード基盤で要件を満たせるなら、そちらを利用するほうが合理的なはずです。

一方、次のような特性を持つアプリケーションでは、導入価値がありそうだと感じました。

- 大量のレコードを検索・編集・操作するリッチなクライアント UI が必要
- 状態やユーザーの権限によって画面構成が変わる
- 独自のデータモデルや業務ロジックを持っている

チケット管理、CRM、社内業務管理、ワークフロー、ダッシュボードなどが挙げられるでしょうか。

## 現時点での限界

もちろん、json-render を導入すれば無条件に開発や保守が簡単になるわけではありません。

まず、Catalog、Registry、UI Spec、State、Action といった複数の要素を管理する必要があります。
通常の Vue なら一つのコンポーネント内で完結する実装が、複数のレイヤーに分かれることもあります。

今回の設計では、この分離自体に価値を見いだしていますが、画面構成が単純で変更も少ないアプリケーションでは、かえって複雑さが増える可能性があります。

また、UI Spec で表現できることは Catalog の定義に依存します。
新しい種類の操作や UI が必要になれば、Spec を変更するだけで済まず、Catalog や Registry、Vue コンポーネント側の実装も必要になる場合があります。

UI を実行時に解釈するため、描画性能やデバッグ体験については検証が必要です。
通常の Vue と組み合わせられるとはいえ、その組み合わせでどこまで問題を避けられるかは、今後検証したいところです。

## おわりに

SDUI 自体は以前からある技術ですが、LLM による Generative UI への需要を背景に、json-render のようなライブラリが登場しました。

そのおかげで今回は、既存のフレームワークに Generative UI 向けのライブラリを組み合わせるだけで、画面構成を配信・描画する仕組みを一から作らずに SDUI を試せました。

しかも、アプリケーション全体を json-render で構築する必要もありません。
画面構成をサーバー側で決めたい部分だけに導入してもいいし、特殊な UI が必要なら普通に Vue で書けばいい。

実用に向けては、どこまでを UI Spec に任せ、どこからを通常の Vue で実装するか。
その分離による利点が、複数の要素を管理するコストに見合うかを確かめたいと思います。
